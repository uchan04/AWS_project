# 아키텍처 — 쉬운 설명

대상: A~E 전원, 그리고 발표에서 "이거 어떻게 만든 거예요"를 받는 사람.
읽는 시간: 7분. 기술 상세는 `docs/architecture.md`에 있다. 이 문서는 **그림**만 본다.

---

## 0. 30초 요약

우리 서비스는 **한 덩어리가 아니다.** AWS의 부품 6개를 조립한 것이고, 각 부품은 **서로 다른 컴퓨터**에서 돈다.

```
        브라우저
           │
           ▼
  ┌────────────────┐
  │  Amplify       │ ← 화면을 만들고 API를 처리한다 (Next.js)
  └───┬───┬───┬────┘
      │   │   │
      ▼   ▼   ▼
  Cognito RDS Bedrock      + S3/CloudFront (그림)
  (신분증) (창고) (챗봇 AI)
```

**부품이 나뉘어 있다는 사실이 이 프로젝트 버그의 절반을 설명한다.** 왜 그런지가 이 문서다.

---

## 1. 식당 비유 — 부품 6개의 정체

우리 서비스를 식당이라고 하자.

| 부품 | 식당의 무엇 | 실제 이름 | 하는 일 |
|---|---|---|---|
| 브라우저 | 손님 | Chrome 등 | 주문한다 |
| **Amplify** | **주방** | AWS Amplify Hosting | 화면을 만들고 요청을 처리한다 |
| Cognito | 입구 신분증 확인 | Amazon Cognito | "이 사람 회원 맞나" |
| **RDS** | **창고** | PostgreSQL 16.4 | 사용자·미션·글을 보관한다 |
| Bedrock | 상담 전문가 | Claude (us-east-1) | 챗봇 답변, 사진 판독 |
| S3 + CloudFront | 창고의 사진첩 + 배달 트럭 | S3 + CDN | 펫 그림, 업로드 사진 |

**핵심: 주방(Amplify)은 자기 힘으로 아무 것도 기억하지 못한다.** 요청이 끝나면 다 잊는다. 기억은 전부 창고(RDS)에 있다.

## 2. 요청 한 번이 지나는 길

사용자가 `/pet`을 열었을 때 실제로 일어나는 일.

```
1. 브라우저 ──────────► Amplify        "펫 화면 주세요"
                          │
2.                        ├─ 쿠키 확인   "로그인했나?"  ← middleware.ts
                          │              안 했으면 /login으로 돌려보냄
                          │
3.                        ├──► RDS      "이 사람 누구? 씨앗 몇 개?"
                          │             ← getCurrentUser()
                          │
4.                        └─ HTML 조립
                          │
5. 브라우저 ◄─────────────┘             화면이 뜬다
                          │
6. 브라우저 ──────────► CloudFront      "펫 그림 주세요"  ← 여기는 Amplify를 안 거친다
```

**6번이 따로 가는 걸 눈여겨보라.** 그림은 주방을 안 거치고 배달 트럭에서 바로 온다. 그래서 **서버 로그에는 그림 요청이 안 찍힌다.** 그림이 안 나올 때 서버 로그를 봐도 아무것도 안 나오는 이유다.

## 3. 왜 버그가 생기나 — 부품 사이의 틈 3개

### 틈 1. 주방은 자기 주소를 모른다

배포된 서버에게 "너 주소가 뭐야?"라고 물으면 이렇게 답한다.

```
localhost:3000
```

**틀린 답이다.** 실제 주소는 Amplify가 준 공개 도메인이다.

왜 이러나: Amplify는 Next.js를 **Lambda라는 작은 상자** 안에서 돌린다. 그 상자 안에서는 자기가 `localhost:3000`으로 돌고 있다. 상자 밖에 공개 주소가 있다는 걸 상자는 모른다.

```
      바깥 세상                    Lambda 상자 안
  https://우리도메인   ──────►   나는 localhost:3000 이다
```

**그래서 "로그인 페이지로 보내줘" 같은 코드가 배포하면 깨진다.** 개발자 노트북에서는 `localhost:3000`이 진짜 주소라서 잘 돈다.

우리 해결: `appOrigin(request)` 함수 하나가 주소를 정한다.

```
1순위  APP_ORIGIN 환경변수     ← 사람이 직접 적어 준 진짜 주소
2순위  x-forwarded-host 헤더    ← 바깥에서 붙여 준 주소 (localhost면 건너뛴다)
3순위  request.url              ← 최후의 수단. 개발용
```

**주소가 필요한 코드는 이 함수만 쓴다.** 직접 `request.url`을 읽지 않는다.

### 틈 2. 브라우저가 주방을 못 믿는다 (CSP)

우리는 보안 헤더를 보낸다. 뜻은 이렇다.

> "브라우저야, 이 목록에 없는 곳에서 온 그림은 버려라."

목록에 CloudFront 주소를 빠뜨렸더니 **펫 그림이 전부 안 나왔다.** 서버는 200을 잘 돌려줬고, 배달 트럭도 그림을 잘 배달했다. **브라우저가 받아서 버렸다.**

```
CloudFront ── 그림 ──► 브라우저 ──► 🗑️   "명단에 없는 주소다"
```

`tsc`·`lint`·`build`·자체 검사 9종이 전부 통과했다. **브라우저를 열어야만 보이는 종류의 버그다.**

우리 해결: 주소를 정하는 함수를 하나로 묶었다 — `cdnOrigin()`이 그림 주소를 만들 때도, 보안 명단을 쓸 때도 같이 쓰인다. **두 곳이 어긋날 수 없게 만든 것이다.**

### 틈 3. 창고 창구가 79개뿐이다

```
RDS가 동시에 말을 걸 수 있는 창구      79개
  − 관리자 예약                        3개
─────────────────────────────────
  앱 몫                               76개

노트북 1대의 개발 서버가 잡는 것       25개  ← Prisma 기본값 (CPU 12 × 2 + 1)
5인이 각자 켜면                       125개  ← 76개를 넘는다
```

**5명이 다 켜면 배포본 몫이 0이 된다.** 시연 중에 배포본이 창고에 접속을 못 한다.

그리고 Prisma는 **한 번 연 창구를 프로세스가 죽을 때까지 안 닫는다.** 실측: 부하를 주니 11 → 23개가 됐고, 부하가 끝나도 23개에서 안 줄었다.

> **시연 전 체크: 5인 전원 로컬 서버 종료.**

## 4. 코드가 부품별로 어디 있나

```
isol-service/
├─ middleware.ts       ← 입구 문지기. 모든 요청이 여기를 먼저 지난다
├─ app/
│  ├─ (화면들)/         ← 브라우저에 보일 것
│  └─ api/             ← 브라우저가 부르는 창구
├─ lib/
│  ├─ auth.ts          ← Cognito 담당. 모든 API의 첫 줄
│  ├─ prisma.ts        ← RDS 담당. 창고 연결
│  ├─ reward.ts        ← 재화 계산. 유일한 경로
│  ├─ assets.ts        ← CloudFront 주소 계산
│  └─ oauth.ts         ← 주소 계산(appOrigin)
├─ prisma/
│  ├─ schema.prisma    ← 창고 설계도
│  └─ seed/            ← 창고 기본 내용물 (미션 909행 등)
└─ scripts/            ← 자체 검사 (check:*, e2e)
```

**`middleware.ts`가 특별하다.** 화면이든 API든 **모든 요청이 여기를 먼저 지난다.** 그래서 여기가 깨지면 하나가 아니라 전부 깨진다. (실제로 그랬다 — `공유DB와-사고-3건.md` 사고 3)

같은 이유로 `lib/auth.ts`의 `getCurrentUser()`도 특별하다. **모든 API의 첫 줄**이라, 이 함수가 죽으면 전부 죽는다. (사고 1)

> 손댈 때 가장 조심할 파일 둘: **`middleware.ts`**, **`lib/auth.ts`**.
> 둘 다 "이 기능만 깨진다"가 성립하지 않는다.

## 5. 배포 — 코드가 사용자에게 닿는 길

```
내 노트북 ──push──► feat/xxx ──merge──► develop ──PR──► main
                                                         │
                                                    Amplify가 감지
                                                         ▼
                                                     자동 빌드
                                                         ▼
                                                     자동 배포 🚀
```

**`main`에 들어가면 바로 사용자에게 간다.** 사람이 배포 버튼을 누르지 않는다.

그래서 두 가지가 따라온다.

1. **빌드가 깨진 커밋이 `main`에 들어가면 배포가 실패하고 전원이 막힌다.** 커밋 전에 `npm run build`.
2. **스키마를 바꿨으면 `main` 머지 *전에* 공유 DB에 적용한다.** 순서가 반대면 배포본이 죽는다. (사고 1)

## 6. 자체 검사 3층 — 무엇이 무엇을 잡나

부품이 나뉘어 있으니 검사도 층이 나뉜다. **위층이 통과해도 아래층이 깨질 수 있다.**

| 층 | 명령 | 무엇을 잡나 | 못 잡는 것 |
|---|---|---|---|
| 1. 문법·타입 | `npx tsc --noEmit`, `npm run build` | 오타, 타입 불일치 | 실행하면 깨지는 것 전부 |
| 2. 순수 함수 | `npm run check:*` (9종) | 계산이 틀린 것 | 요청이 지나는 길 |
| 3. 실제 요청 | `npm run e2e` (서버 필요) | 라우트·인증·리다이렉트 | **브라우저가 하는 일** |
| 4. 눈 | 브라우저를 연다 | 그림·글꼴·CSP·레이아웃 | — |

사고 3에서 **1·2층이 전부 통과하고 3층만 걸렸다.** CSP 사고에서는 **1·2·3층이 전부 통과하고 4층만 걸렸다.**

> **미들웨어·인증·라우트를 만졌으면 3층까지. 화면 결과물을 바꿨으면 4층까지.**

## 7. 발표에서 물어볼 만한 것

| 질문 | 한 줄 답 |
|---|---|
| 서버 관리는 어떻게 하나요 | 안 한다. Amplify가 Lambda로 알아서 띄운다(서버리스). `main`에 머지하면 자동 배포다 |
| 챗봇은 어떤 모델인가요 | Amazon Bedrock의 Claude. 우리가 모델을 학습시키지 않고 API로 부른다 |
| 사진은 어디 저장되나요 | S3(비공개). 브라우저는 CloudFront를 통해서만 본다 — 버킷 자체는 인터넷에 안 열려 있다 |
| DB가 죽으면요 | RDS 관리형이라 백업·복구가 AWS 쪽에 있다. CloudWatch로 CPU 70% 알람을 걸어 뒀다 |
| 확장 가능한가요 | 계산(Amplify)은 자동으로 늘어난다. **병목은 DB 커넥션 79개다** — 이 숫자를 아는 것이 답의 핵심이다 |
