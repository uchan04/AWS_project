## 1. 안전 판정을 한 모듈이 소유하게 한다 (가장 중요)

### 지금 상태

```
lib/safety.ts (138줄, fan-in 9)         app/community/_lib/moderation.ts (469줄)
  isCrisis()                              moderate()          ← BLANKET 정책 + LLM 판정
  containsAbuse()          ◄──import──    findProfanity()
  CRISIS_POST_NOTICE                      containsChosungAbuse()
                                          containsGestureAbuse()
```

**욕설 검출기가 두 벌이고, 우선순위가 어느 모듈에도 없다.** 라우트가 3층을 손으로 쌓는다.

```
posts/route.ts        111 containsAbuse→400 │ 126 moderate→400 │ 155 isCrisis→안내
comments/route.ts      54 containsAbuse→400 │  60 moderate→400 │  86 isCrisis→안내
                       └──── 위기 글이 여기서 끊긴다 ────┘   └ 도달 못 함 ┘
```

### 목표 형태

판정을 하나로 모아 **우선순위를 모듈의 성질로 만든다.**

```ts
// lib/safety.ts — 이미 fan-in 9인 공용 모듈이다. 여기가 제자리다
export type Judgement = {
  verdict: "OK" | "WARN" | "BLOCK" | "SELF" | "CRISIS"
  message: string | null   // 차단 문구
  notice: string | null    // 상담 안내(109). CRISIS일 때만 채운다
}

/** 위기가 욕설을 이긴다. 그 규칙이 이 함수 안에만 있다 */
export async function classify(text: string, invoke?: BedrockInvoke): Promise<Judgement>
```

라우트는 이렇게 줄어든다.

```ts
const j = await classify(`${title}\n\n${body}`, invokeBedrock)
if (j.verdict === "BLOCK") return fail(BLOCK_CODE, j.message!, 400)
// ... post 생성 ...
return ok({ post, crisisNotice: j.notice })
```

### 왜 이 형태인가

- **`check:safety`가 우선순위를 단정할 수 있다.** 지금은 순수 함수 3개를 따로 단정할 수만 있고
  "둘이 섞였을 때 무엇이 이기나"를 단정할 자리가 없다 — `e2e`도 못 잡는 이유가 같다
- **라우트가 늘어도 재발하지 않는다.** 지금은 세 번째 라우트가 3층을 다시 손으로 쌓는다
- **정책은 D의 것을 그대로 유지한다**(2026-08-24 사용자 결정). 옮기는 것은 판정 위치뿐이고
  `POLICY = "BLANKET"`·사전·정규화·LLM 판정은 한 글자도 안 바꾼다

### 순서와 주의

1. `lib/safety.ts`에 `classify()`를 추가한다. **기존 `isCrisis`·`containsAbuse`는 지우지 않는다**
   (fan-in 9. `Bonfire.tsx`·`ChatPanel.tsx`·`systemPrompt.ts`도 쓴다)
2. `check:safety`에 우선순위 단정을 넣는다 — **위기+욕설 입력이 `CRISIS`로 나오는지**
3. 라우트 2곳을 갈아탄다. `e2e`에 섞인 글 단정 1건
4. `moderation.ts`는 `classify()`의 내부 구현으로 남긴다 — 파일을 옮기지 않는다

**소유:** `lib/safety.ts`는 담당 표에 없다. `app/community/`는 D다. **착수 전에 D와 합의한다.**

## 2. `grantAffinity()`를 `lib/`로 옮긴다

### 지금 상태

```
lib/reward.ts          calculateReward()  ·  capAffinity()    ← 상한 계산
app/community/_lib/    grantAffinity()                         ← 지급 실행 (기능 전용 폴더)
     affinity.ts
```

쓰는 쪽이 3곳이다 — 커뮤니티 글·댓글, 챗봇(`app/api/chat/messages`, `ChatPanel.tsx`),
모임 신청(`meetups/[id]/join`). **담당 폴더를 넘는 유일한 import가 이것이다.**

`lib/reward.ts`가 "재화 증감의 유일한 경로"로 `lib/`에 있는 것과 비대칭이고,
**상한과 지급이 갈라져 있어서 이미 버그 주석이 붙어 있다** — `posts/route.ts:142~145`:

> `completeMission`은 하루 상한을 넘겨받은 `actor.affinityToday`(메모리 값)로 계산하는데
> … 이 호출이 낡은 `affinityToday`를 보고 하루 상한 100을 넘길 수 있다.

### 목표 형태

`lib/affinity.ts`로 옮기고 상한·지급을 한 모듈이 갖는다. `capAffinity()`도 함께 옮겨
`lib/reward.ts`는 배율만 남긴다.

### 주의

- **`lib/reward.ts`는 C 소유 공용 파일이다**(`CLAUDE.md` 1절). `capAffinity`를 옮기면
  시그니처 변경이므로 전원 통보가 필요하다
- 옮기는 것만으로 위 상한 버그가 낫지는 않는다. **읽기를 DB 기준으로 바꾸는 것이 실제 수정**이고,
  그건 별건이다. 여기서는 그 수정을 **한 곳에서 할 수 있게 되는 것**이 이득이다
- 곁가지: `app/community/_lib/format.ts`를 chat이 쓴다. 같이 `lib/`로 옮길 후보

## 실행 순서 제안

```
1번(안전 판정)  →  3번(진단 게이트)  →  2번(친밀도)
```

1번이 먼저인 이유: 사용자에게 실제 해가 가는 유일한 항목이고, 다른 둘과 파일이 겹치지 않는다.
2번이 마지막인 이유: `lib/reward.ts`(C 소유)를 건드리는 유일한 항목이다.

**세 항목 모두 착수 전에 해당 소유자와 합의한다.** 재배치는 코드 이동이라 충돌이 크고,
이 팀에서 대형 충돌 해결은 기능 하나를 새로 만드는 것보다 오래 걸린다(`CLAUDE.md` 4절).
