## 4단 진화로 변경 (2026-08-21)

**3단 → 4단으로 늘렸다.** 2026-08-20 S3 실측에서 종당 4장(`-1`~`-4`)이 나왔고 `stageCount`는 3이라 `-4`가 참조되지 않는 파일로 떠 있었다. E에게 확인하니 **4단 진화가 계획된 것**이었다. 즉 어긋난 쪽은 S3가 아니라 코드·명세였다.

### 확정값

| 항목 | 값 | 근거 |
|---|---|---|
| 4단 레벨 | **Lv.25** | 누적 씨앗 3,000 = 수급 약 109/일 기준 약 27일 |
| 단계 이름 | **알 · 아기 · 청소년 · 성체** | 사용자 결정. 이전 3개(아기·청년·전설)는 폐기 — 최종 단계는 "전설"이 아니라 "성체"다 |
| 2·3단 | Lv.5 / Lv.15 그대로 | 기존 값을 건드리지 않았다. 4단만 얹었다 |

누적 씨앗은 `5 × N × (N-1)`이다(`expToNextLevel = level × 100`, 씨앗 1 = 경험치 10에서 나온다). Lv.15 = 1,050, **Lv.25 = 3,000**이다.

**Lv.25를 고른 이유는 상점 속도와의 균형이다.** 3단이던 때 씨앗은 9일이면 끝나 펫이 먼저 완주하고 남는 재화가 됐다. 4단 27일이면 스킨 2500 별조각(39일)·배경 3600 친밀도(36일)와 세 축이 모인다. Lv.20(1,900 · 17일)은 여전히 펫이 혼자 빨랐고 Lv.30(4,350 · 40일)은 3단→4단 구간만 3,300씨앗으로 비어 있었다.

### 고친 곳

| 파일 | 무엇 |
|---|---|
| `lib/types.ts` | `EVOLUTION_LEVEL`에 `STAGE4: 25` 추가, `evolutionStageFor()`에 `>= 25 → 4` 분기 |
| `prisma/seed/items.ts` | 6종 `stageCount: 3` → `4` |
| `lib/pet.ts` | `applySeeds()` 기본 인자 `stageCount = 3` → `4` |
| `app/api/pet/route.ts`·`feed/route.ts`·`app/pet/page.tsx` | `?? 3` → `?? 4` (활성 스킨이 없을 때의 폴백) |
| `app/pet/_components/PetView.tsx` | `STAGE_NAME`·`STAGE_DESC` 4개, `MAX_STAGE` 상수 도입, `stageRange()`·`nextMilestone()`에 4단 분기 |
| `app/pet/pet.css` | `[data-stage]` 크기를 3구간 → 4구간(5.5 / 7 / 8.5 / 10rem) |
| `scripts/check-pet.ts` | `STAGE4 = 25`, 경계 6개, 누적 1,050·3,000, `stageCount === 4` 단정 |
| `SPEC.md` | 5절 성장·수급량 표·스킨 절, 11절 `PetSkin.stageCount` |

**`Math.min(..., 3)` 하드코딩을 `MAX_STAGE = STAGE_NAME.length`로 바꿨다.** 이번에 3이 박힌 곳을 찾느라 파일 8개를 훑었다. 다음에 단계를 또 늘리면 `STAGE_NAME`에 한 줄 넣는 것으로 화면 쪽은 끝난다.

### `lib/types.ts`를 브랜치에서 고쳤다 — A에게 알려야 한다

`EVOLUTION_LEVEL`과 `evolutionStageFor()`가 **A 소유 공유 파일**에 있다(`CLAUDE.md` 1절). 규칙대로면 A가 `main`에 직접 커밋해야 하는데, 마감이 하루 남아 **사용자 승인을 받고 C가 `feat/pet`에서 직접 고쳤다.** 규칙을 바꾼 것이 아니라 이번 한 번의 예외다.

바꾼 것은 그 파일에서 **성장 곡선 블록 한 군데뿐이다**(74~84줄 부근). `TypeCode`·`TRIBE`·`Adjective`·닉네임 상수는 손대지 않았으므로 A가 같은 파일을 고쳤어도 충돌 지점이 겹칠 가능성은 낮다. 그래도 **머지 시점에 이 파일을 먼저 확인한다.**

### 남은 것: 실 DB의 `stageCount`

시드 파일만 4로 고쳤고 **실 DB의 `PetSkin` 6행은 아직 3이다.** 이 상태에서는 `cappedStage()`가 3에서 자르므로 Lv.25에 도달해도 화면은 3단에서 멈춘다(`check-pet.ts`가 `cappedStage(25, 3) === 3`으로 이 동작을 못 박아 뒀다 — 조용히 4로 새지 않는다). `npm run db:seed` 한 번이면 `upsert`가 6행을 4로 덮어쓴다. 공유 DB 쓰기라 승인 대기 중이다.

## Figma 디자인 이관 (2026-08-21)

사용자가 Figma에서 만든 펫 홈 시안을 `/pet`에 씌웠다. 받은 것은 Figma **Make**의 소스 export(`Downloads/Create pet home design/`)다.

**export 폴더를 레포에 넣지 않았다.** 그건 Vite + React 19 + Tailwind v4 앱이고 `src/App.tsx` 한 파일에 909줄이 들어 있다. 레포 안에 두면 Next 빌드와 `tsconfig`가 그 파일들을 주워 가고, `main`에 올라가면 5인 전원의 빌드가 그 폴더를 컴파일한다. **컴포넌트 모양만 베껴 왔고 폴더는 레포 밖에 그대로 뒀다.**

**export의 로직은 버렸다.** 시안은 씨앗을 `setUserSeeds(prev - amount)`로 화면 상태에서 깎고 경험치를 `amount * 8`로 계산한다. 재화 증감은 `calculateReward()`만 통과한다(`CLAUDE.md` 2절)는 규칙 정면 위반이고 비율도 `SEED_TO_EXP = 10`과 다르다. **API 호출부(`/api/pet/feed`·`/api/pet/idle`)는 이관 전 코드를 그대로 유지했다** — 이번 작업은 화면 이관이고 서버 계약은 손대지 않았다.

### 색은 시안 색이 아니라 종족색을 따른다

시안은 전부 주황(`#E07A45`)이다. 그건 **여우 유형 데모 화면**이고, 고양이·곰 유저가 열면 진단 결과와 어긋난 색이 뜬다. 그래서 요소 모양만 같게 두고 색은 `styles/tokens.css`의 `[data-tribe]`에서 나오는 `--tribe`를 쓴다(`PetView.tsx` 루트에 이미 `data-tribe={typeCode}`가 있었다). `style={{ backgroundColor }}`를 쓰지 않는다는 기존 규칙 그대로다.

`--tribe` 원색(`#E8956A`)에 흰 글자를 얹으면 명암비가 **2.35:1**로 AA(4.5:1)에 한참 못 미친다. 시안의 주황이 더 진한 색이었기 때문에 그대로 옮기면 안 된다. 그래서 흰 글자가 올라가는 면은 전부 `--tribe-cta`(종족색 58% + ink)를 쓴다.

```css
.pet {
  --tribe-cta:   color-mix(in oklch, var(--tribe) 58%, var(--color-ink));  /* 흰 글자용 */
  --tribe-line:  color-mix(in oklch, var(--tribe) 40%, var(--color-card)); /* 테두리 */
  --tribe-soft:  color-mix(in oklch, var(--tribe) 22%, var(--color-card));
  --tribe-wash:  color-mix(in oklch, var(--tribe) 12%, var(--color-paper));
}
```

**종족색을 따르지 않는 것도 있다.** 방 배경의 바닥(나무), 창밖 하늘, 화분 잎은 고정색이다. 여기까지 `--tribe`를 넣으면 고양잇과 유저에게 파란 나무와 파란 화분이 나온다. 벽·커튼·러그만 종족색을 따른다.

**씨앗 초록과 상점 나무색은 새 색 계열이라 `pet.css` 안에 뒀다.** `styles/tokens.css`는 A 소유이고 파일 끝에 덧붙이면 A도 같은 자리에 덧붙여 머지 충돌이 난다(`3bc8541` 때와 같은 판단). 씨앗 버튼은 시안의 `#7BB86A`에 흰 글자면 2.2:1이라 `--pet-seed: #4a7a3c`(5.07:1)로 낮췄고, 게이지 채움에만 밝은 원색을 쓴다.

### Tailwind 유틸리티 → 의미 클래스

시안은 유틸리티 클래스로 짜여 있는데 이 프로젝트 화면은 전부 의미 클래스(`.hm-*`)다. Tailwind v4가 이미 깔려 있어(`@tailwindcss/postcss` + `app/globals.css`의 `@import "tailwindcss"`) 유틸리티를 그대로 붙여도 빌드는 되지만, 한 화면만 다른 방식으로 짜 두면 다음 사람이 어느 규칙을 따를지 모른다. `.pet-*` 클래스로 다시 썼다. **새 의존성은 추가하지 않았다.**

시안 `index.css`의 `@theme inline` 토큰들은 실제로는 인라인 `style`의 `var()`로만 읽히고 있었다(쓰인 Tailwind 클래스는 전부 기본 클래스였다). 그래서 `@theme`가 필요 없고 `.pet` 스코프의 일반 커스텀 프로퍼티로 옮겼다 — **E 소유인 `app/globals.css`를 건드리지 않았다.**

기존 `.hm-pet`·`.hm-pet__cos`·`.hm-pet__evolve`는 지우지 않았다. `app/pet/skins`와 `app/pet/cosmetics`가 아직 쓴다.

### 방 배경 = 착용한 배경 치장, 기본값은 SVG 방 (2026-08-21 사용자 확정)

**배경 6종(`배경1`~`배경6`)을 상점에서 사서 착용하면 그 그림이 방 배경이 된다. 착용 전까지는 Figma 시안으로 만든 SVG 방이 기본 배경이다.** 그래서 이 SVG는 버리는 임시물이 아니라 **미착용 유저의 정식 화면**이다(지금 `UserCosmetic`이 0행이라 전원이 이 방을 본다). 다만 더 예쁘게 다듬는 데 시간을 쓸 자리는 아니다.

- **카펫은 배경에 속하는 요소다.** 다른 배경 그림에는 카펫이 없으므로 별도 레이어로 빼지 않고 `PetRoom.tsx` 안에 둔다 — 배경이 갈리면 카펫·바닥·창도 함께 갈린다
- **펫은 배경과 무관하게 방 중앙 하단에 고정한다.** 배경마다 바닥 높이가 다르므로 어느 한 그림에 맞춰 좌표를 잡지 않았다. `flex` 흐름에 두면 이름·설명 줄 수에 따라 펫이 흔들려서 `.pet-char`를 `position: absolute` + `bottom` + `left: 50%`로 심었다
- **배경 이미지는 기본 방 SVG를 지우지 않고 그 위에 덮는다.** 이미지가 안 뜰 때(CloudFront 403·미업로드) 빈 방이 되지 않게 하려는 것이고, `onError`로 `<img>`가 스스로 숨으면 아래 방이 다시 보인다. 대신 **배경 그림은 불투명 전체 그림이어야 한다** — 투명 PNG면 두 방이 겹친다. 그 경우에도 아래가 새어 나오지 않게 `.pet-room__bg--img`에 불투명 바닥을 깔아 뒀다
- **이름·설명에 반투명 바닥을 깔았다.** 배경 6종이 어떤 밝기로 올지 몰라서, 어두운 그림이 와도 글자가 읽히게 했다
- URL은 `app/pet/page.tsx`가 만든다. 착용 행 중 `slot === "BACKGROUND"`인 것의 `imageKey`를 CloudFront 도메인에 붙인다(`imageKey`에 확장자가 이미 있다 — `cosmetics/bg-1.png`). 슬롯당 1개라 첫 행이 유일하다
- **펫 그림은 손댈 것이 없다.** `pet.imageUrl`(CloudFront `<imageKeyBase>-<단계>.png`)이 있으면 `<img>`를 쓰고 없을 때만 이모지로 떨어진다. S3 파일과 `imageKeyBase`만 맞으면 된다 — 단 `pets/bear-polar`(시드) ↔ `pets/bear-arctic`(S3 실제) 불일치 때문에 **북극곰만 이모지로 떨어진다**(차단 19번)

**남은 것은 이미지 6장을 S3 `cosmetics/bg-1.png` ~ `bg-6.png`로 올리는 것뿐이다.** 이름이 맞으면 코드를 더 고치지 않는다.

### 방 배경은 새 컴포넌트로 뺐다

`app/pet/_components/PetRoom.tsx`. 벽·줄무늬·바닥 판자·창·커튼·화분·러그를 SVG로 그린다. `aria-hidden`이고 색은 인라인이 아니라 클래스(`.pet-room__wall` 등)로 줘서 `pet.css`가 `var(--tribe)`로 칠한다.

**시안의 커튼은 실제로 안 그려지는 코드였다.** `App.tsx:46-47`이 `<path d="M 72% 5% Q ...">`인데 SVG path의 `d`는 퍼센트를 받지 않는다. 브라우저가 조용히 무시해서 커튼 두 장이 없는 화면이 나온다. `viewBox="0 0 400 300"` 좌표계로 다시 썼다.

씨앗 투입 프리셋은 시안의 1/5/10/20을 **1/10/50/100**으로 바꿨다. 1→2 레벨업이 씨앗 10개이고 일일 미션이 하루 60개를 주므로 20이 최대치면 레벨업 한 번에 버튼을 여러 번 눌러야 한다.

**이 화면은 primary CTA가 하나가 아니다.** `design.md`의 "화면에 primary는 하나" 규칙에서 의도적으로 벗어난 자리다. 받기·먹이기·상점 2개가 동시에 필요한 게임 HUD라서 역할별 색으로 구분했다(accent = 먹이기, 씨앗 초록 = 방치형 수령, 나무색 = 상점). 코드에 주석으로 남겼다.

## 배고픔 게이지 (2026-08-21)

`SPEC.md` 5절에 절을 추가했다. **표시 전용이고 재화·경험치·진화에 영향을 주지 않는다.**

**값을 저장하지 않는다.** `User.lastFedAt`(마지막 급여 시각) 하나만 두고 배고픔은 `lib/pet.ts`의 `hungerFor(since, now)`가 계산한다. 값을 저장하면 화면을 열 때마다 감쇠분을 써야 해서 조회가 쓰기가 된다 — 방치형 씨앗을 페이지 로드에서 지급하지 않는 것과 같은 이유다.

- 24시간에 걸쳐 100 → 0 선형 감쇠. 하루 한 번 들여다보면 유지된다
- **투입 개수는 배고픔에 영향이 없다.** 1개를 먹여도 100이다. "얼마나 먹였나"는 경험치가 이미 표현한다
- **0이 되어도 페널티가 없다.** 벌점형 압박은 랭킹을 배제한 것과 같은 이유로 이 서비스 대상에 맞지 않는다. 페널티를 넣으려면 `SPEC.md` 5절을 먼저 고친다
- `lastFedAt`이 `null`인 유저는 화면이 `createdAt`을 넘긴다. 신규 유저에게 0을 보여 주면 시작부터 굶긴 것처럼 보인다
- 시계 오차로 기준이 미래면 감쇠하지 않는다(`idleAccrual`과 같은 방어)

**마이그레이션은 손으로 썼다.** `prisma/migrations/20260821090000_pet_last_fed_at/migration.sql`에 `ALTER TABLE "User" ADD COLUMN "lastFedAt" TIMESTAMP(3);` 한 줄이다. `npx prisma migrate dev`는 스키마 담당 1인만 실행한다(`CLAUDE.md` 5절). nullable 컬럼 추가라 기존 행을 건드리지 않는다.

`prisma/schema.prisma`는 전원 합의 파일이라 원래 손대지 않지만, 이 컬럼은 **사용자 지시로 추가했다.** `SPEC.md` 11절 표에도 같이 넣었다(`CLAUDE.md` 1절이 요구한다).

`npm run check:pet`이 감쇠 곡선(0/6/12/18/24시간 = 100/75/50/25/0), 클램프, 미래 시각, `null`, 라벨 경계(60·30)를 못 박는다.

**별조각 60은 아직 구현되지 않았다 (B 담당).** `lib/missions/completion.ts:128`이 TODO다. 그게 들어가기 전에는 별조각 수급이 출석 3.6/일뿐이고 스킨 2500은 **약 700일** — 상점이 사실상 잠긴다. 가격은 이미 실 DB에 들어갔으므로 **지금 남은 것은 수급 쪽 하나뿐이다.**

**치장 가격은 등급에서 파생시킨다.** `prisma/seed/items.ts`의 `PRICE_BY_RARITY`가 유일한 출처이고 `upsert`가 매번 `priceAffinity`를 덮어쓴다. 아이템을 추가할 때 가격을 손으로 적지 않는다 — 등급만 정하면 된다. 등급을 새로 만드는 것은 `Rarity` enum 변경이라 전원 합의가 필요하다.

**COMMON만 600으로 올리지 않고 RARE 이상도 10배로 올렸다** (600 / 1000 / 1800 / 2800). COMMON만 올리면 RARE(100)가 COMMON보다 싸져 등급 순서가 뒤집힌다. 지금 6종이 전부 COMMON이라 쓰이지 않는 값이지만, 뒤집힌 표를 남기면 나중에 등급만 바꾼 사람이 가격이 내려간 것을 모른다. `check:pet`이 오름차순을 단정한다.

**실 DB 반영 기록 (2026-08-20).** 사용자 승인을 받고 `npm run db:seed`를 한 번 돌렸다. 출력은 `옛 치장 12종 삭제: ... / 스킨 6종, 치장 6종 반영 / 미션 41개 반영 / seed 완료`이고, `UserCosmetic`이 0행이라 보유자 경고는 나오지 않았다(=유저 데이터 손실 없음). 이후 실 DB 확인 결과 변종 스킨 3종 `별조각가=2500`, `CosmeticItem` 6행 전부 `BACKGROUND`·`COMMON`·`친밀도가=600`(합 3600)이다. **이제 시드 파일과 실 DB가 일치한다 — 다시 어긋나게 두지 않는다.**

## 치장 구매 (2026-08-20)

`POST /api/pet/cosmetics/buy`를 만들었다. 이게 없어서 치장 화면이 늘 "미획득"이던 문제(옛 `docs/STATUS.md` 차단 9번)가 닫혔다.

`app/api/pet/skins/buy/route.ts`를 베꼈고 다른 점은 두 가지다.

- **종족 검사가 없다.** 치장은 종족 구분이 없어 누구나 산다(`tribeColor` 삭제, 결정 변경 14번)
- 차감 재화가 `starShards`가 아니라 `affinity`다. 부족하면 `NOT_ENOUGH_AFFINITY`

같이 유지한 것: 이미 보유 시 유니크 제약 500 대신 `400 ALREADY_OWNED`, 연타 방어용 조건부 `updateMany`(`affinity >= price`를 `where`에), 소비이므로 `calculateReward()` 미경유.

**판단한 것 네 가지**

1. **`User.affinityToday`는 건드리지 않는다.** 그 값은 "오늘 얼마나 벌었나"를 세는 일일 상한 카운터다(하루 100. `SPEC.md` 5절). 소비로 되돌리면 사고 다시 벌어 하루 상한을 무한히 우회할 수 있다
2. **가격을 코드에 적지 않는다.** 라우트도 화면도 DB의 `priceAffinity`만 읽는다. 등급별 표를 여기 복사하면 `PRICE_BY_RARITY`와 갈라진다
3. **`affinityOnly`와 `priceAffinity !== null`을 둘 다 확인한다.** 지금 시드는 6종 전부 판매품이지만, 나중에 이벤트 지급 아이템(가격 없음)이 들어오면 0원 구매가 된다. 화면도 그 경우 버튼 대신 "미획득"을 띄운다
4. **사면서 입히지 않는다.** `equipped`는 기본값 `false`다. 슬롯당 1개 규칙 때문에 사는 순간 착용 중인 것이 벗겨지면 유저가 되돌릴 수 없다. 착용은 `POST /api/pet/cosmetics`가 따로 한다

화면(`CosmeticList.tsx`)도 같이 고쳤다. 상단에 친밀도 잔액을 띄우고, 미보유 타일에 "친밀도 60" 버튼을 붙였다. 잔액이 모자라면 버튼이 `disabled`가 되고 문구가 "친밀도 N 부족"으로 바뀐다 — 눌러 보고 에러를 받는 것보다 먼저 아는 게 낫다. 구매 성공 시 잔액·수집 진행률을 **서버가 돌려준 값으로** 맞춘다(클라이언트에서 빼서 계산하면 서버와 갈라진다). `GET /api/pet/cosmetics`도 `affinity`를 같이 내려준다 — `GET /api/pet/skins`가 `starShards`를 내려주는 것과 같은 형태다.

## 치장 12종 → 배경 6종 (2026-08-20)

모자·목도리를 컷하고 배경 6종만 남겼다. 이름은 `배경1`~`배경6`, 등급은 6종 전부 `COMMON`이라 가격은 각 친밀도 600(합계 3600)이다.

- **왜**: 치장 이미지 12장을 8/22까지 만들 수 없다. 슬롯이 하나면 "슬롯당 1개" 규칙이 곧 "배경 하나 고르기"가 되어 화면도 단순해진다
- **왜 등급을 안 갈랐나**: 배경 6종은 서로 대체재다. 어느 쪽이 좋은지 없는 아이템에 가격 차이를 두면 유저가 얻는 정보 없이 비싼 쪽이 늦어지기만 한다. 다시 가르려면 시드의 `rarity`만 바꾼다(가격은 `PRICE_BY_RARITY`에서 따라온다)
- **가격은 60 → 600이 됐다 (2026-08-20 팀 결정).** 합계 3600이고 친밀도 일 상한이 100이라 배경 하나에 6일, 전부 36일이다. 녹화용 수집 진행률 화면은 데모 계정 시드로 만든다
- **`Slot` enum은 안 건드렸다.** `HAT`·`SCARF`를 스키마에 그대로 뒀다. 시드에서 안 쓰면 행이 생기지 않아 마이그레이션이 필요 없고, `schema.prisma`는 전원 합의 파일이다(`CLAUDE.md` 1절). `lib/pet.ts`의 `COSMETIC_SLOT_ORDER`와 화면의 슬롯 카드 루프도 3슬롯을 유지한다 — 아이템이 없는 슬롯은 카드를 그리지 않으므로 화면에는 배경 카드 하나만 뜬다
- **화면 코드는 고칠 것이 없었다.** 목록·진행률 분모·정렬이 전부 `CosmeticItem` 행에서 파생돼 있었다

### 시드가 옛 행을 지운다 (`pruneCosmetics()`)

`upsert`는 `name`이 유니크 키라 새 6행만 만들고 옛 12행을 남긴다. 그대로면 화면에 **18종**이 뜨고 진행률 분모도 18이 된다(둘 다 `CosmeticItem` 행 수에서 나온다). 그래서 `seedItems()`가 `upsert` 전에 시드 목록에 없는 행을 지운다.

- **보유자(`UserCosmetic`)가 있는 행은 지우지 않는다.** FK 때문에 `deleteMany`가 터지고, 남의 보유 이력을 시드가 조용히 날리면 되돌릴 수 없다. 그 경우는 경고만 찍고 사람이 판단한다 — 시드는 유저 데이터를 지우지 않는다
- 깨끗한 DB에서도, 이미 6종만 있는 DB에서도 아무 일도 하지 않는다(멱등). 5인 누가 돌려도 같은 결과가 된다
- 실 DB의 `UserCosmetic`은 **0행**이었다(2026-08-19 확인, 8/20 시드 때도 경고가 안 나와 재확인됨). 그래서 옛 12종 전부가 삭제됐고 되돌릴 유저 데이터는 없었다 — 가장 싼 시점에 처리했다

**실 DB 반영 완료 (2026-08-20).** `npm run db:seed` 한 번으로 옛 12행이 삭제되고 `배경1`~`배경6`(각 600)이 들어갔다. 같은 시드가 스킨 가격도 50 → 2500으로 올렸다(둘 다 사용자 승인 범위였다). 상세는 위 "재화 배정 확정" 절의 반영 기록.

`npm run check:pet`이 구성을 못 박는다: 6종 · 전부 `BACKGROUND` · 전부 `COMMON` · `COMMON = 600` · 합계 3600 · 등급 가격 오름차순 · 변종 스킨 전부 2500 · 이름 `배경1`~`배경6` · 정렬 결과. 이를 위해 `COSMETICS`와 `PRICE_BY_RARITY`를 `export`했다(`PET_SKINS`와 같은 방식이고, 그 파일은 `@prisma/client`를 type으로만 import하는 순수 데이터라 DB 없이 읽힌다).

정렬 단정에 있던 옛 아이템 이름(노을 모자 등)은 실재하지 않게 됐다. 비교 함수는 3슬롯을 그대로 처리하므로 슬롯·등급 순서 커버리지는 남기고, 픽스처 이름만 "가상 모자"처럼 실재하지 않음이 드러나는 값으로 바꿨다.

## 스킨 이름 어미 단정 (2026-08-20)

`lib/pet.ts`의 `animalEmoji()`는 이름의 **어미**로 기본 동물을 찾는다(북극여우 → 여우 → 🦊). 변종마다 이모지를 새로 적지 않기 위한 설계다.

문제는 이 규칙이 깨지는 방식이 조용하다는 것이다. 어미가 종족명이 아닌 이름("스노우폭스")을 시드에 넣으면 예외가 나지 않고 발자국(🐾)이 뜬다. 빌드도 lint도 통과하고 화면만 이상해진다.

그래서 `scripts/check-pet.ts`가 `prisma/seed/items.ts`의 `PET_SKINS`를 직접 읽어 단정한다.

- 이름 어미 = `TRIBE[typeCode].animal`
- `animalEmoji(name)` = `TRIBE[typeCode].emoji` (어미 규칙을 지켜도 typeCode가 어긋나면 여기서 걸린다)
- `stageCount`는 전부 3, 기본 외형은 이름이 동물명 그대로 + `priceShards === null`, 변종은 `priceShards > 0`
- 종족마다 기본 1종 + 변종 1종 (한쪽이 빠지면 그 종족은 상점이 비거나 펫이 없다)

이를 위해 `PET_SKINS`를 `export`했다. 그 파일은 `@prisma/client`를 **type으로만** import하는 순수 데이터라 체크 스크립트가 DB 커넥션 없이 읽는다 — `check:pet`이 DB를 모르는 순수 검증으로 남는다.

**아직 런타임 검증은 못 했다.** 확인한 것은 `npm run build`, `tsc --noEmit`, `eslint app/pet`, `check:pet`·`check:reward`·`check:diagnosis` 통과까지다. 씨앗 투입·레벨업·진화 연출을 브라우저에서 실제로 돌려보지는 않았다 — 유저 `밤바다`의 `seeds`가 0이라 씨앗을 넣을 수 없고, 씨앗을 채우는 것은 공유 DB 쓰기라 승인이 필요하다.

**어긋난 것 두 가지.**

1. **북극곰만 키가 다르다.** 시드는 `pets/bear-polar`, S3는 `pets/bear-arctic`이다. 여우·고양이는 `-arctic`으로 맞는다. 이대로 이미지를 붙이면 북극곰 스킨만 깨진다. 고치는 쪽은 시드 한 줄(`prisma/seed/items.ts`) + 실 DB `imageKeyBase` UPDATE다. S3 파일명을 바꾸는 쪽은 E의 버킷이고 CloudFront 캐시까지 걸리므로 시드를 맞추는 편이 싸다. **이름 어휘도 `북극여우`·`북극고양이`와 같은 `-arctic`으로 통일되므로 이쪽이 맞다.** 다만 시드 파일은 공유 파일이라 사용자 승인 후 고친다.
2. **종당 4장이다.** `-4`가 전부 있는데 `PetSkin.stageCount`는 전부 3이고 `SPEC.md` 5절은 3단 진화(5레벨 2단 / 15레벨 3단)로 확정이다. `-4`는 명세에 없는 단계다. E가 여유분으로 만든 것인지 4단 진화를 염두에 둔 것인지 확인이 필요하다. **`stageCount`를 4로 올리는 것은 명세 변경이라 팀 결정 사항이고, C가 혼자 바꾸지 않는다.** 그냥 두면 `-4`는 아무도 참조하지 않는 파일로 남는다(동작에는 지장 없다).

**실 DB에는 이미 `북극고양이`로 들어가 있었고, 어긋나 있던 쪽은 시드 파일과 문서였다.** 확인 결과 실 DB는 6종 전부 정상이다(`북극고양이 / INDEPENDENT_LOW_INCOME / 2500 / pets/cat-arctic / 3단 / NONE`, 보유자 0). 샴고양이 행은 없다 — 즉 옛 이름 행이 남아 목록에 7종이 뜨는 상태가 아니다.

**시드 재실행으로 개명하지 않는다.** `seedItems()`의 upsert는 `name`이 유니크 키라서, 시드에서 이름만 바꾸고 `db:seed`를 돌리면 새 행이 생기고 옛 행이 그대로 남는다. 치장에는 `pruneCosmetics()`가 있지만 **스킨에는 정리 코드가 없다**(`prisma/seed/items.ts` 17~19줄 경고). 개명이 필요하면 `UPDATE`로 제자리에서 바꾼다.

`DELETE` + `CREATE`도 안 된다. `UserPetSkin.petSkinId`와 `User.activePetSkinId`가 `PetSkin.id`를 가리키므로(이름이 아니다) 행을 새로 만들면 id가 바뀌어 보유 이력과 착용 상태가 끊긴다. 제자리 `UPDATE`는 id를 유지한다.

같은 이유로 `animalEmoji()`는 그대로 동작한다 — `북극고양이`의 어미가 `고양이`라 `check-pet.ts`의 어미 단정도 통과한다. 개명할 때 어미를 깨는 이름(`아크틱캣` 등)을 고르면 화면에 조용히 🐾가 뜬다.

남은 옛 이름 두 곳은 내 소유가 아니라 손대지 않았다 — `prisma/schema.prisma:171` 주석 예시(전원 합의 파일), `docs/dev/diagnosis.md`(A 담당, 별조각 50 시절 기록이라 값도 함께 낡았다).

## 결정한 것과 이유
- `calculateReward`는 `User`가 아니라 `PetSkin | null`을 받는다. `User`만 받으면 함수가 async가 되어 호출부 4명이 전부 바뀐다
- 성장: **씨앗 1 = exp 10**, 필요 exp = 레벨 × 100, 5레벨 2단 / 15레벨 3단
- **씨앗→경험치 비율을 1:1 → 1:10으로 변경 (2026-08-19).** 배율은 `lib/pet.ts`가 아니라 `lib/types.ts`의 `SEED_TO_EXP`에 있다(A 소유 공유 파일). `applySeeds()`는 상수를 참조만 하므로 `lib/pet.ts`는 손대지 않았다. A 브랜치가 그 줄을 건드리지 않은 것을 `git diff`로 확인한 뒤 사용자 승인을 받아 `main`에서 고쳤다 — **A에게 통보 필요**. 소비자는 `lib/pet.ts` 하나뿐이라 다른 담당 코드에는 영향이 없다
  - 밸런스: 1→2 레벨업 씨앗 10개, 3단 진화(15레벨)까지 누적 1,050개 (이전 10,500개)
  - `SPEC.md` 5절도 같이 갱신했다 (5절은 C 담당 절)
  - `scripts/check-pet.ts`는 값만 바꾸면 의도가 깨지는 케이스가 있어 씨앗 수를 다시 잡았다. "레벨업 직전"과 "소수점 버림"은 레벨업이 없는 구간이어야 의미가 있어 99→9, 10.9→9.9로 바꿨다. 비율을 또 바꾸면 이 두 개를 먼저 확인한다
  - 비율 자체를 못 박는 `assert.equal(SEED_TO_EXP, 10)`을 추가했다. 상수가 조용히 바뀌면 여기서 먼저 걸린다
- 캐릭터는 유형 제한 없이 3종 모두 구매 가능
- **씨앗 투입은 `calculateReward()`를 통과하지 않는다.** 저 함수는 재화를 *획득*할 때 배율을 얹는다. 투입은 쓰는 쪽이라 배율을 얹으면 10개를 넣었는데 11개가 빠진다. `SPEC.md` 6절의 통과 대상 목록(미션·방치형·출석·친밀도)에도 투입은 없다. `CLAUDE.md` 2절 위반처럼 보이므로 라우트에 이유를 주석으로 남겼다
- 성장 계산을 `lib/pet.ts` 순수 함수로 뺐다. DB·요청 객체를 모르게 유지해야 `check:pet`으로 검증할 수 있다
- 씨앗 차감과 성장 반영은 한 트랜잭션이고, 트랜잭션 안에서 잔액을 다시 읽는다. 버튼 연타로 두 요청이 겹치면 잔액보다 많이 빠질 수 있다
- 레벨 여러 개가 한 번에 오를 수 있어 `while`로 처리한다 (씨앗을 몰아 넣는 경우). `level`이 0 이하로 들어오면 필요 exp가 0이 되어 무한 루프가 되므로 1로 클램프한다
- GET 응답의 `evolutionStage`는 저장값이 아니라 레벨에서 다시 계산한다. 미션 보상이 씨앗만 올리고 단계를 갱신하지 않는 경우에 화면이 어긋나지 않게 한다
- `app/pet/page.tsx`에 `force-dynamic`을 넣었다. 없으면 빌드 시점에 DB 미연결 안내가 정적으로 굳어 DB가 붙은 뒤에도 그대로 나온다

**지금 가장 급한 것: `lastFedAt` 마이그레이션이 실 DB에 안 들어갔다.**

`migrate dev`가 아니라 `deploy`다(`CLAUDE.md` 5절: `migrate dev`는 스키마 담당 1인만). `migrate reset`은 공유 DB 데이터가 전부 지워지므로 어떤 경우에도 쓰지 않는다. **C가 임의로 공유 DB에 쓰지 않고 승인을 기다린다.** 적용 전까지 화면 검증은 불가능하다 — 지금까지 확인한 것은 `npm run build`·`tsc --noEmit`·`eslint`·`check:pet` 통과까지다.
